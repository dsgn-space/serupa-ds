# Settings section

One group of settings with its own heading, its own Save, its own status and its own error summary. A settings page stacks several.

<Canvas of={Stories.Default} />

## When to use it

- A settings page with a few groups that people change one at a time: profile, notifications, billing.
- Not for a setting that should apply the moment it's switched, such as dark mode. Use a Switch on its own there, and say what changed.
- Not for one long form that's sent once, such as sign-up. That has one Save at the end.

## What each part is for

- **A region named by its heading**, so a screen reader lists each group and can jump to it. The description says what the group is for. Pick `headingLevel` to fit the page's outline. The error summary's heading is one level below it.
- **Its own Save.** Nothing saves until it's pressed (3.2.2), and it saves only this section, so a half-finished change in another one is left alone. While saving, the button shows a loader and can't be pressed twice.
- **SaveStatus** beside the button says "Saved", or "Couldn't save" with Try again (`onRetry`). Screen readers hear it once, politely, without focus moving (4.1.3).
- **An error summary** at the top of the form when a save fails, listing each problem as a link to its field. It takes focus, so it's read out and seen (3.3.1). Pass each field its own `error` too, so the message is next to the field (3.3.3).
- **Another language**: `saveLabel` changes the button's word. SaveStatus and the summary's heading come from Serupa's own labels.
- **On a phone**, the heading sits above the fields. On a wide screen, it sits beside them (1.4.10).

## What stays your app's job

- Checking the fields and writing each error so it says how to fix the problem ("Enter an email address like name@example.com").
- Saving, then setting `status` to `'saving'`, `'saved'` or `'error'`.
- Warning before someone leaves the page with unsaved changes, if losing them would hurt.
