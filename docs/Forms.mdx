# Forms

A form asks people for something, tells them clearly when an answer won't do, and keeps what they typed. Each component below handles its own part. This page is how the parts work together, with links to the details.

[Form](?path=/docs/components-forms-form--docs) does most of this page for you: give it a schema (Zod, Valibot or ArkType) and it checks each field at the right moment, shows the summary on a failed submit, and maps the server's errors onto their fields. [Build a form](?path=/docs/guides-build-a-form--docs) walks through sign-up, checkout and settings with it.

## Labels

- Every control has a visible label: wrap it in a [Field](?path=/docs/components-forms-field--docs). A row checkbox in a table, with no room for one, takes an `aria-label` instead.
- Keep labels short and specific: "Work email", not "Please enter your email address".
- Put format help in the Field's `hint` ("Like name@example.com"), never only in a placeholder, which goes as soon as someone types.
- A set of checkboxes or radios that answer one question is one Field with `group`, so its label becomes the fieldset's legend.

## Required and optional

Mark both. Put `required` on every field that must be filled (a `*`, and `aria-required` for screen readers) and `optional` on every field that can be left empty ("(optional)"), even when most fields are one kind. People skim past the line that explains a convention, so a form that marks only one kind leaves them guessing about the rest, and the words on each field help most those who find forms hard. Say once before the form what the `*` means ("Fields marked * are required."), since a sign alone isn't self-explanatory. A sign-in form, or a form of one field, needs neither.

## When to check

- Check a field when someone leaves it or submits the form, never on every keystroke: an error that appears while people are still typing tells them off for something they haven't finished.
- A field someone tabs past without typing isn't an error yet: leave it alone until they submit. An empty required field flagged on the way through tells them off for a field they haven't reached.
- Once a field shows an error, check it again as they type, so the error goes as soon as the answer is right.
- Say what's wrong and how to fix it: "Enter a date in the future", not "Invalid date". The same words go in the field's error and in the summary.

## When the submit fails

1. Show an [ErrorSummary](?path=/docs/components-forms-errorsummary--docs) at the top of the form, listing the problems in the order of the fields. It takes focus, so everyone, screen reader users included, learns the submit failed, and each line links to its field.
2. Show the same message on each field, with the Field's `error`.
3. Prefix the page's `<title>` with "Error: " while the summary shows.
4. Keep everything people typed. Never clear a form because one field is wrong.

A short form of one or two fields can skip the summary: move focus to the first field with an error instead.

## Sending and saving

- The submit [Button](?path=/docs/components-actions-button--docs) shows `loading` while the form is sent, and blocks a second click, so nothing is sent twice. A promise from `onClick`, or a React form `action`, does this by itself. Keep its label as it was ("Save changes"), so the width doesn't jump.
- A form that saves as people go, with no Save button, shows a [SaveStatus](?path=/docs/components-feedback-savestatus--docs) near its title: Saving, Saved, or an error with Try again.
- A form in a [Dialog](?path=/docs/components-overlays-dialog--docs) takes `unsaved` while it has changes, so closing it by accident asks "Discard changes?" first.
- When the save fails for a reason that isn't a field, say so with an [Alert](?path=/docs/components-feedback-alert--docs) at the top of the form, and keep the changes. [Messages and feedback](?path=/docs/guides-messages-and-feedback--docs) says which message to use when.

## The right keyboard and autofill

On a phone, the keyboard that comes up decides how hard a field is to fill. Say what the field holds, and the browser shows the matching keys and offers what it already knows.

| The field holds | Use | What people get |
| --- | --- | --- |
| An email address | [Input](?path=/docs/components-forms-input--docs) `type="email"`, `autoComplete="email"` | A keyboard with @ and the dot, no capital first letter, their address offered |
| A phone number | [PhoneInput](?path=/docs/components-forms-phoneinput--docs) | The phone keypad, and `autoComplete="tel"` already set |
| A whole number or an amount | [NumberInput](?path=/docs/components-forms-numberinput--docs) | Digits, with the decimal key only when the field takes decimals |
| A code sent by text or email | [PinInput](?path=/docs/components-forms-pininput--docs) | Digits, and the code offered above the keyboard (`one-time-code`) |
| Digits that aren't an amount: a card number, a postal code | Input with `inputMode="numeric"` | Digits, with no steppers and no thousands separators |
| A web address | Input `type="url"` | A keyboard with the slash and ".com" |
| A search | [SearchInput](?path=/docs/components-forms-searchinput--docs) | A Return key that says Search |
| A password | [PasswordInput](?path=/docs/components-forms-passwordinput--docs) with `autoComplete="current-password"` or `"new-password"` | The password manager fills or suggests one |

- **Name what the field is with `autoComplete`** whenever it's about the person filling it in: `name`, `email`, `tel`, `street-address`, `postal-code`, `cc-number`. People then fill a form with one tap, and WCAG 1.3.5 asks for it. Turn it off (`autoComplete="off"`) only for a field about someone else, such as a customer's address typed by support.
- **Say what Return does with `enterKeyHint`** when it isn't the default: `next` in a run of fields, `send` in a message box, `done` on the last field, `go` for an address. SearchInput sets `search` itself.
- **Leave spelling help on for prose and off for codes.** Input already turns off capital letters and spelling for email, URL, user name and code fields; set `autoCapitalize="words"` on a name field, and `spellCheck={false}` on anything that isn't words (a coupon, a serial number).
- **Never block paste**, least of all in a password or a code field: a password manager and a texted code both arrive by paste.
- **Fill in what you already know**, such as the country from the account, or the email the person signed in with, and let them change it.

## A list of things to fill in

Phone numbers, line items, team members to invite: people add, change and remove entries of one kind. Pick the layout by how many fields one entry has.

| One entry has… | Use |
| --- | --- |
| 1 to 3 short fields that need no label each | Rows with a Remove button on each and "Add another" after the last. Name each row's fields for screen readers ("Phone 2") |
| 2 to 5 fields that fit across the page | An editable table, a row per entry: a [DataGrid](?path=/docs/components-content-datagrid--docs) with editable cells |
| 6 to 8 fields | An [Accordion](?path=/docs/components-content-accordion--docs), a panel per entry, named after it ("Ada Lovelace, admin"), the one being edited open |
| More than 8 | The entries in a list or a table, each edited in a [Drawer](?path=/docs/components-overlays-drawer--docs) or on its own page |

- "Add another" stays after the last entry, and adding one moves focus to its first field.
- Removing an entry moves focus to the entry before it, or to "Add another" when none is left, and can be undone ([Destructive actions](?path=/docs/guides-destructive-actions--docs)).
- Say the limit before people reach it ("Up to 5 numbers"), and keep at least one entry when one is required.

## With a form library or a server action

Form is the simplest way ([Build a form](?path=/docs/guides-build-a-form--docs)). The fields also work without it:

Serupa's fields are native form controls underneath, so they work with a plain `<form>`, a React form `action` and form libraries without adapters. Wire each piece by what it is:

| The field | Submits | With React Hook Form |
| --- | --- | --- |
| Input, Textarea, PasswordInput, Select, Checkbox, Radio, Switch | Its own native control, under its `name` | `{...register('email')}`: the ref and events reach the native control |
| NumberInput, Slider, Combobox, DatePicker, DateRangePicker, TimePicker, PhoneInput | A hidden input with its `name`: the number, the option's value, the date as `YYYY-MM-DD` | A `Controller`, passing `value` and `onValueChange` |

```tsx
<form onSubmit={handleSubmit(save)} noValidate>
  <Field label="Work email" error={errors.email?.message}>
    <Input type="email" {...register('email', { required: 'Enter your work email' })} />
  </Field>
  <Controller name="country" control={control} rules={{ required: 'Choose a country' }} render={({ field, fieldState }) => (
    <Field label="Country" error={fieldState.error?.message}>
      <Combobox options={countries} value={field.value ?? null} onValueChange={field.onChange} onBlur={field.onBlur} ref={field.ref} />
    </Field>
  )} />
  <Button type="submit">Save</Button>
</form>
```

**Errors from the server.** Wrap the form in `FormErrors` and give it the errors by field name, as the server answered: each Field inside shows its own, an `ErrorSummary` with no `errors` of its own lists them and takes focus, and a field's message goes as soon as it's edited. A schema validator's field errors fit as they are (with Zod, `error.flatten().fieldErrors`, taking the first message of each).

```tsx
const [state, action] = React.useActionState(saveProfile, { errors: null });

<form action={action}>
  <FormErrors errors={state.errors}>
    <ErrorSummary />
    <Field label="Display name"><Input name="displayName" /></Field>
    <Field label="Birthday"><DatePicker name="birthday" /></Field>
    <Button type="submit">Save</Button>
  </FormErrors>
</form>
```

The submit Button shows `loading` by itself while a form `action` runs. Whichever way the errors come, the rules above still hold: check on leaving a field, never on each keystroke, and keep what people typed.

## Do and don't

| Do | Don't |
| --- | --- |
| "Work email", with "Like name@example.com" as the hint | "Please enter your email address here", with the format only in the placeholder |
| Show the error when someone leaves the field | Show "Invalid email" after the first letter |
| "Enter your full name" | "Name is invalid" |
| `inputMode="numeric"` for a card number | `type="number"`, whose arrows and scroll wheel change the number |
| Keep the answers when the submit fails, and focus the summary | Clear the form, or leave focus on the button with nothing said |
| `*` on required fields and "(optional)" on the rest | Only "All fields are required unless marked" at the top |
